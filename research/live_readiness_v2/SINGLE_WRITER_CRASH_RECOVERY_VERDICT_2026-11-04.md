## Mandatory caveats — why no LIVE GO
1. **SQLite lease ownership applies only to processes coordinating through the same correctly shared LOCAL database**. SQLite WAL on network filesystems and multiple independent hosts is not an accepted production fencing solution. A holder's Python PID and UUID are not robust operator authentication or non-forgeable capability tokens.
2. Transactions serialize local journal mutations, NOT an exchange order already in flight. A stale worker might send an external request after a local fence check. Since this prototype contains NO broker adapter, **external exactly-once execution or stop placement is NOT proved**. Requires dedicated executor, broker-side idempotency where available, account-order reconciliation, and fencing at the irrevocable side-effect boundary.
3. A power failure is represented by **abrupt process exit**. True power removal, disk corruption, filesystem caching, Windows service kill/upgrade, shared disk and durable off-host archival were NOT tested. SQLite FULL is not a guarantee against all filesystem or hardware failures.
4. The recovery flag `mock_flat_confirmed=True` is a synthetic paper fixture, **not independent verification that a real MEXC account is flat**. Need read-only broker positions, open orders, active protective stops, partial fills, contract mode and actual execution fee schedule; ambiguous states must remain frozen, not force cleared.
5. The new proof is independent of the existing `risk_firewall.py`. It is not wired to a production adapter or a signed Telegram supervisor. No automated shadow fills, funding reconciliation, real native stop ACKs, drawdowns or independent economic validation.
6. Before any future live consideration: prove a positive independent after-cost signal, production-grade risk integration, native stop semantics, live account reconciliation, durable cross-host lease if distributed, operator authentication, emergency-response runbook and explicit final dated authorization.
